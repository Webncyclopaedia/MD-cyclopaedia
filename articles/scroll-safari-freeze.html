Safari (iOS): страница «залипает» на первом экране — скролл мёртв

Реальный кейс из практики: Vite + React SPA, тёмный лендинг с SVG-хиро на 100svh, деплой на Vercel. Тестовое устройство — iPhone 11. На десктопе всё работало идеально — проблема была только на телефоне, и только в Safari.

Симптом

Страница открывается, первый экран отрисован, но свайп/колесо ничего не делают — документ зафиксирован на нулевой позиции скролла. Chrome на том же телефоне скроллил нормально. Важная улика: при прямом заходе на /project/:id (другое дерево компонентов, хак не применялся) — скролл живой. Значит, виноват не браузер сам по себе, а то, что конкретная страница делает с документом.

При каких условиях появляется

В коде был вот такой легаси-хак:

// Portfolio.tsx — при монтировании
[document.documentElement, document.body, root]
  .forEach((el) => { el.style.height = "100%"; el.style.margin = "0"; });

плюс в глобальном CSS:

html, body, #root {
  min-height: 100vh;
  overflow-x: hidden; /* ← на трёх уровнях сразу */
}

Триггерная комбинация:

  1. height: 100% на <html> и <body> (не min-height) — корень становится жёстко-фиксированным боксом, весь контент «переполняет» его;
  2. overflow-x: hidden одновременно на html и body. По спецификации, если одна ось hidden, вторая вычисляется в auto — то есть и html, и body претендуют на роль скролл-контейнера, плюс клип пропагируется на viewport. В iOS WebKit это даёт конфликт моделей прокрутки: движок не может решить, кто скроллит документ.

iOS Safari прокручивает документ относительно viewport с rubber-band-логикой, и когда корень — клипующий бокс фиксированной высоты, тач-скролл документа просто блокируется. Chrome/Blink прощает эту конфигурацию, WebKit — нет.

Как диагностировали (метод, пригодится вам)

В консоли Safari — три проверки:

document.body.style.height        // "" — если что-то есть, это подозреваемый №1
getComputedStyle(document.body).overflowX
window.scrollTo(0, 2000); window.scrollY   // 0 при живом scrollHeight = скролл сломан

И контрольный эксперимент, который закрыл диагноз: прямо на живой странице document.body.style.height = "" — скролл мгновенно ожил. Причина подтверждена, а не угадана.

Фикс

  1. Убрать JS-хак с height: 100% полностью — он не нужен: min-height: 100vh в CSS уже есть, а margin: 0 у body ставит любой reset (Tailwind preflight).
  2. overflow-x с корня документа (html/body) — снять вообще. Горизонтальный overflow, если он есть, клипуется на обёртках контента через overflow-x: clip: clip не создаёт скролл-контейнера, поэтому position: sticky и нативный скролл документа не страдают (пара visible + clip разрешена спецификацией именно поэтому).

Выводы (чек-лист)

  1. overflow-x: hidden — только в одном месте и никогда на html+body парой. Нужен горизонтальный клип — overflow-x: clip на обёртке контента.
  2. Не управлять высотой html/body из JS. Хаки «поставим height: 100%, чтобы что-то растянулось» на корне документа — мина для iOS WebKit.
  3. Если баг воспроизводится на одной странице, но не на другой — сравнивайте, чем отличаются деревья компонентов и какие стили/скрипты они применяют к документу. Эта улика сузила поиск до одного компонента.
  4. Диагностика мобильных WebKit-багов без DevTools: консольные проверки (inline styles, computed overflow, scrollTo-тест) + контрольный эксперимент «обнули подозреваемый стиль прямо на живой странице».
  5. Chrome/Blink прощает то, что WebKit не прощает: «работает в Chrome на телефоне» — не аргумент, проверяйте в Safari.
