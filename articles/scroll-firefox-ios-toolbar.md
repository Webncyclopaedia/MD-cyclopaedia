# Firefox на iPhone: контент дёргается вместе с тулбаром

> Реальный кейс из практики: Vite + React SPA, тёмный лендинг с SVG-хиро на `100svh`. iPhone 11. Первый экран собран из абсолютно позиционированных элементов внутри хиро во всю высоту экрана. Симптом — только в Firefox на iPhone; в Safari на том же телефоне всё чисто, на десктопе — тем более.

## Симптом

При старте скролла контент первого экрана «дёргается» — причём строго синхронно с анимацией скрытия нижней тулбарки Firefox. Свайп вниз — тулбар уходит, содержимое хиро (имя, профиль, подсказка скролла) сдвигается рывком. Свайп вверх — тулбар возвращается, рывок в обратную сторону. Скролл при этом работает — страница не залипает, но визуально первый экран «плавает».

## Ключевой факт, который всё объясняет

**На iPhone все браузеры — WebKit внутри.** Apple обязывает сторонние браузеры рендерить через WKWebView, «свой движок» у Firefox/Chrome на iOS отсутствует. Поэтому любые баги тут — баги WebKit-энвайронмента, а не «кривой Firefox».

Разница между Safari-приложением и Firefox на iOS — в управлении тулбарами:

- **Safari**: тулбары — нативная часть WebKit. Когда они прячутся, layout viewport остаётся стабильным, юниты `svh`/`vh` не пересчитываются, лэйаут не двигается.
- **Firefox iOS**: тулбар — часть UI приложения. Его скрытие/появление = **ресайз всего WKWebView-фрейма**. А когда ресайзится сам WebView, пересчитывается всё: `svh`, `vh`, `dvh`, `lvh` — для встроенного WebView понятие «стабильный small/large viewport» фактически отсутствует.

## При каких условиях появляется

Достаточно одного видимого элемента, размер которого привязан к viewport-юнитам. У нас это hero:

    .hero {
      height: 100svh; /* ← в Firefox iOS это динамическая высота */
    }

Цепочка: свайп → тулбар начал прятаться → WKWebView ресайзится на ~60–120px → `100svh` пересчитывается → hero меняет высоту → абсолютно позиционированные имя, профиль, подсказка скролла сдвигаются → визуальный рывок. `min-height: 100vh` на секциях ниже фолда в этот момент тоже меняются, но это незаметно (меняется только общая высота документа) — поэтому «прыгает» именно первый экран.

## Ложный след, на который стоит потратить ваше время, чтобы не тратить своё

Первой гипотезой был `overflow-x`: перепробовали варианты «overflow на html», «на body», `hidden` vs `clip` — симптом не уходил. Виноват был вообще не overflow, а пересчёт viewport-юнитов. Маркер, который указывает на настоящий источник: рывок строго коррелирует с показом/скрытием тулбара, а не с самим скроллом.

## Фикс

CSS-ом не лечится (любой viewport-юнит в этом энвайронменте динамический). Лечится фиксацией высоты в пикселях с игнорированием «тулбарных» ресайзов:

    useEffect(() => {
      const hero = heroRef.current;
      if (!hero) return;

      const isTouch = window.matchMedia("(pointer: coarse)").matches;
      const threshold = isTouch ? 150 : 0; // тулбар ~60–120px < 150 → игнор
      let lockedHeight = window.innerHeight;

      const apply = () => { hero.style.height = `${lockedHeight}px`; };
      const onResize = () => {
        const h = window.innerHeight;
        if (Math.abs(h - lockedHeight) < threshold) return;
        lockedHeight = h;
        apply();
      };
      const onOrient = () => requestAnimationFrame(() => {
        lockedHeight = window.innerHeight;
        apply();
      });

      apply();
      window.addEventListener("resize", onResize);
      window.addEventListener("orientationchange", onOrient);
      return () => {
        window.removeEventListener("resize", onResize);
        window.removeEventListener("orientationchange", onOrient);
        hero.style.height = "";
      };
    }, []);

Нюансы решения:

- **Порог 150px** — эмпирический: тулбары мобильных браузеров в пределах ~120px, реальные события (поворот, ресайз окна) больше. На десктопе порог 0 — высота всегда под окно.
- `orientationchange` обрабатываем отдельно через `requestAnimationFrame` — сразу после поворота `innerHeight` ещё старый.
- Инлайн-высота снимается при анмаунте, CSS-фолбэк `100svh` остаётся для первого кадра.
- `min-height: 100vh` на остальных секциях трогать не нужно — их изменение не видно глазу. Фиксируем только то, что реально видно пользователю.

## Выводы (чек-лист)

1.  «Баг в Firefox на iPhone» — это почти никогда не Gecko: на iPhone все браузеры рендерят WebKit-ом. Если в Safari на том же телефоне всё ок — виновата не вёрстка движка, а то, _как_ приложение управляет WebView (тулбары, ресайз фрейма).
2.  `svh`/`vh`/`dvh` в браузерах на встроенном WKWebView — динамические: любой элемент, заметный на экране и привязанный к viewport-юнитам, будет «плавать» при показе/скрытии тулбара. Критичные первые экраны фиксируйте в px с пороговым обработчиком `resize`.
3.  Маркер настоящего источника — корреляция симптома с тулбаром, а не со скроллом. Если рывок совпадает с анимацией тулбара — забудьте про overflow, ищите viewport-юниты.
4.  Фиксируйте высоту только видимых элементов первого экрана: невидимые изменения `min-height` ниже фолда пользователей не беспокоят, а лишний JS — лишняя точка отказа.
5.  Порог в обработчике `resize` подбирайте по физике тулбаров (~120px максимум) — он отличает «тулбарный» ресайз от настоящего (поворот, смена окна).
